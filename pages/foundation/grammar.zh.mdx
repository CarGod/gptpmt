## 先接受一件事：模型不会读心术

模型只能根据收到的指令、上下文、可用工具和训练中学到的模式生成结果。任务里缺少的信息，它可能追问，也可能猜测。

提示工程的一个基本原则是：**减少不必要的猜测，同时让结果可以检查。**

下面六个技巧不要求每次全部使用。任务越简单，Prompt 可以越短；任务越复杂，越需要明确边界和验收标准。

## 技巧一：明确目标和使用场景

不要只说一个宽泛动作，要说明要解决什么问题，以及结果给谁使用。

| 宽泛表达 | 更清楚的表达 |
| --- | --- |
| 帮我写一封邮件 | 给已经提交退款申请的客户写一封回复邮件，说明已经收到申请和下一步需要补充的材料 |
| 总结这份文档 | 为没有参加会议的项目负责人整理一份摘要，突出已经确认的决定、风险和待办事项 |
| 检查代码 | 检查这段 Python 代码为什么在空列表输入时出错，先解释原因，再提供最小修改方案和测试用例 |

“2021 年的美国总统是谁”这类带固定年份的问题，和“现在的总统是谁”不同。后者属于会变化的事实，应要求查询可靠的当前来源并注明日期。

## 技巧二：提供必要的上下文和输入

模型不知道你所在团队的术语、内部规则和目标读者。只提供完成任务必须知道的背景，并删除无关或敏感信息。

```text filename="Prompt" copy
目标：把产品更新说明改写成面向普通用户的通知。

背景：读者不熟悉技术术语；这次更新不会改变现有数据。

输入：
“同步模块改为增量写入，首次启动后重建本地索引。”
```

如果模型需要依据某份材料回答，就把材料提供出来，或明确允许它使用什么检索工具。不能一边要求“只能根据原文”，一边不给原文。

## 技巧三：使用分隔符划清边界

输入较长时，使用 Markdown 标题、三引号、代码块或成对标签，把“指令”和“待处理内容”分开。

```text filename="Prompt" copy
请总结 <article></article> 中的内容。只总结原文明确表达的观点。

<article>
我们测试了新的注册流程。移动端完成率有所提高，但目前样本只来自内部测试，不能推断正式用户也会得到相同结果。
</article>
```

标签有助于阅读，但不会自动阻止错误或恶意指令。外部网页、邮件和文件仍应按不可信输入处理。

## 技巧四：把复杂任务拆成可检查的步骤

如果任务包含多个依赖关系，说明先做什么、后做什么，以及什么时候应该停止。

```text filename="Prompt" copy
请处理下面的客户反馈：

1. 提取客户明确描述的问题；
2. 列出客户明确提出的诉求；
3. 对照我提供的售后规则判断下一步；
4. 如果缺少判断所需的信息，列出缺少项，不要猜测；
5. 生成给客服内部使用的处理建议。
```

拆解步骤不等于要求模型展示完整内部思维。真正需要的是可核验的事实、规则、必要中间结果和最终答案。

## 技巧五：用示例说明难以描述的要求

分类边界、语气和复杂输出格式有时很难只用一句规则说清楚。可以提供少量高质量示例。

```text filename="Prompt" copy
请把反馈分类为“功能问题”“体验建议”或“其他”。

示例：
输入：点击保存后页面提示失败，重试仍然一样。
输出：功能问题

输入：希望搜索结果可以按更新时间排序。
输出：体验建议

现在分类：
输入：你们周末有客服吗？
输出：
```

示例必须覆盖真正容易混淆的边界，而且不能包含错误答案。模型可能模仿示例中的偏差。

## 技巧六：定义输出与验收方式

说明结果需要怎样交付，并告诉模型怎样算完成。

```text filename="Prompt" copy
输出要求：
- 使用 Markdown 表格；
- 列为：问题、严重程度、原文依据、建议动作；
- 严重程度只能是 high、medium、low；
- 原文没有的信息写“未提供”；
- 最后列出仍需人工确认的事项。
```

模型通常比精确字符数更容易遵守“3 个要点”“2 个短段落”这类结构要求。如果发布平台有严格字数限制，应在生成后使用程序或人工再次计数和编辑。

对于程序读取的结果，优先定义 JSON Schema 或其他结构，并执行解析和业务校验。对事实性结果，要求来源和日期，再打开原始来源核对。

## 角色和风格应该怎样写？

角色不是六个必选技巧之一，而是可选的上下文。

```text
请用高中物理教师面向 15 岁学生的方式解释黑洞形成，不使用高等数学；把“事件视界”和“逃逸速度”分别用一句话解释。
```

这里真正有效的是受众、知识范围和表达要求。“你是诺贝尔天体物理学奖得主”既包含不存在的奖项名称，也没有直接定义怎样回答。若确实需要角色，可以写“你是一位天体物理学科普作者”，同时仍需给出具体任务和边界。

## 一个完整的修改案例

修改前：

```text
帮我总结用户反馈。
```

修改后：

```text filename="Prompt" copy
请为产品经理总结 <feedback></feedback> 中的用户反馈。

<feedback>
更新以后启动快了，但第一次打开搜索时等了很久。我找不到清除历史记录的入口，希望能放到设置页。
</feedback>

要求：
1. 分成“正面反馈、问题、建议”三个部分；
2. 每条结论附一段原文依据；
3. 不要推断用户设备、地区或使用频率；
4. 使用 Markdown；
5. 最后列出需要进一步询问用户的问题。
```

修改后的 Prompt 不只是更长，而是明确了读者、输入边界、分类方式、禁止推断的内容和交付格式。

## 本章检查清单

- 是否说明结果给谁使用、解决什么问题；
- 是否提供了完成任务必要的上下文；
- 指令和待处理材料是否容易区分；
- 多步骤任务是否明确了顺序和停止条件；
- 示例是否正确并覆盖关键边界；
- 输出格式和验收标准是否可以检查；
- 是否说明未知信息不能猜测；
- 是否为事实、计算和结构化数据安排了复核方式。
